# ADR-0003: Matching an existing layout in C4-PlantUML was not a success

**Status:** Proposed
**Date:** 2026-10-28
**Deciders:** AIGF maintainers
**Related:** [ADR-0002](0002-interim-diagram-formats-before-calm.md), [ADR-0004](0004-risk-ids-on-diagram-components.md)

## Context

Under [ADR-0002](0002-interim-diagram-formats-before-calm.md), C4-PlantUML is the default interim format when the available layout engines produce a diagram that is easy to understand. The multi-agent reference architecture began in draw.io, and the experiment was to see whether a C4-PlantUML version could be made to keep that arrangement.

Two versions were built:

- **Names only:** component names, arranged like the draw.io diagram.
- **With risks:** the same layout, plus RI-N risk IDs on each component and two risk notes.

Both rendered, and both eventually passed 14 automated checks against the draw.io arrangement, such as "Knowledge left of the runtime" and "LLM below MCP". But:

- **The layouts were found by search, not design.** Graphviz, PlantUML's default layout engine, treats most layout hints as preferences and rearranges boxes to reduce arrow crossings. Small edits rearranged the whole diagram.
- **One arrow could not be drawn.** Feedback → Adaptive Learning broke the layout in all six ways it was tried.
- **The result was harder to read than the Structurizr version** of the same diagram ([ADR-0006](0006-overview-diagram-styling-and-arrow-routing.md)).

## Decision Drivers

- **Don't commit fragile files.** A file whose layout breaks when someone adds an arrow is a maintenance trap.
- **One copy of the risk mapping.** A second diagram-as-code version would mean keeping two copies in step ([ADR-0004](0004-risk-ids-on-diagram-components.md)).
- **Keep what was learned.** The findings are useful to anyone who tries the same thing.

## Considered Options

### Option A: Commit the PlantUML versions as secondary diagrams

- Advantages: a version in the same notation as the AI Governance Framework's diagrams, for people working in PlantUML tooling such as VS Code.
- Disadvantages: fragile layouts, a missing arrow, and a second copy of the risk mapping.

### Option B: Don't commit them, and record the findings here (chosen)

- Advantages: no fragile files in the repository; the lessons are kept.
- Disadvantages: no PlantUML version of this diagram.

## Decision Outcome

**Option B.** The PlantUML versions of the multi-agent diagram are not committed. The Structurizr model is the only diagram-as-code version of it.

The findings below are for anyone who tries to make a C4-PlantUML diagram match an existing picture.

### What it took to hold the layout

- **Hints across boundaries are weak.** A "same row" hint such as `a -[hidden]right-> b` is often ignored when `a` and `b` are in different `Boundary` blocks.
- **Declaration order matters, and swapping it doesn't simply mirror the result.** Moving a single declaration or hint could flip the whole diagram left to right.
- **An invisible boundary kept the runtime's core components together.** Without it, Graphviz slotted the Tools Layer in between them. The technique is `AddBoundaryTag("invisible", $borderColor="transparent", $fontColor="transparent", $bgColor="transparent")`, applied to a `Boundary(..., "", $tags="invisible")` around the boxes that belong together.
- **Arrows can be load-bearing.** The dashed telemetry arrows held the side columns in place. Changing them to `norank` moved those columns.
- **Extra arrows need `norank`.** Four extra arrows only fitted when declared as `-[norank]->`, which keeps them out of Graphviz's placement calculations.
- **ELK doesn't help.** `!pragma layout elk` ignored the hints and stacked the diagram into a single column.

### How the layout was found

Hand-tuning didn't converge, so variants were generated by changing four things:

- the order in which layers are declared;
- how the side columns are tied to the main column;
- how the side arrows constrain placement;
- the order of nested sub-boxes.

Each of 648 variants was rendered to SVG. Box positions were read from the SVG text and scored against the 14 placement checks. Rendering took about 2.3 seconds per variant, so the whole search ran in a few minutes.

### Rendering lessons for any C4-PlantUML diagram

- **Raise the size limit for large diagrams.** By default PlantUML silently crops images wider or taller than 4096 pixels. Render with `java -DPLANTUML_LIMIT_SIZE=8192 -jar plantuml.jar -tpng <file>`.
- **Pin the C4-PlantUML include to a release tag.** The common form `https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Container.puml` follows `master`, so a diagram's rendering can change whenever that project changes.

## Consequences

- **If someone revisits this,** for example with a newer layout engine, start from these findings, and judge success by readability and robustness to edits, not just by matching positions.
- **For other diagrams, PlantUML stays the default.** These findings show what forcing a layout costs; they are not a reason to avoid PlantUML. A diagram that reads well with automatic layout should use C4-PlantUML ([ADR-0002](0002-interim-diagram-formats-before-calm.md)).
